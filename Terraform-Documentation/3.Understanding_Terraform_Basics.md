# 3. Understand Terraform basics:

To get started with Terraform, it's important to grasp the core components and how they work together. Terraform is a powerful Infrastructure as Code (IaC) tool that enables you to define, provision, and manage infrastructure using simple configuration files.

## 3(a). Install and version Terraform providers:

Installing Terraform is a straightforward process, and HashiCorp (the creators of Terraform) provides excellent official instructions. Here's a summary of the most common methods for different operating systems:

#### General Recommendations:

* **Always download from the official HashiCorp website:** https://developer.hashicorp.com/terraform/install This ensures you get legitimate and up-to-date binaries.
* **Verify the installation:** After following the steps, always run terraform -v or terraform version in your terminal to confirm it's installed correctly and shows the version number.


**Installation Method in Linux Operating System:**

For RHEL/CentOS/Fedora (using yum or dnf):

1. Install yum-utils (or dnf-plugins-core for Fedora):
```
sudo yum install -y yum-utils # For RHEL/CentOS/Amazon Linux
# OR
sudo dnf install -y dnf-plugins-core # For Fedora
```

2. Add the official HashiCorp Linux repository:
```
sudo yum-config-manager --add-repo https://rpm.releases.hashicorp.com/RHEL/hashicorp.repo # For RHEL/CentOS/Amazon Linux
# OR
sudo dnf config-manager --add-repo https://rpm.releases.hashicorp.com/fedora/hashicorp.repo # For Fedora
```

3. Install Terraform:
```
sudo yum -y install terraform # For RHEL/CentOS/Amazon Linux
# OR
sudo dnf -y install terraform # For Fedora
```

4. Verify installation:
```
terraform version
```

### 1. Terraform Block:

The terraform block in a Terraform configuration file is a top-level block that configures settings related to Terraform itself, rather than any specific cloud provider or resource. It tells Terraform how to behave when running, including:

### What the terraform block is used for:

|| Description|
|:----|-----|
|**Specifying required Terraform version**| Ensures the configuration only runs with compatible versions.|
|**Declaring required providers** | Tells Terraform what providers to use (like AWS, Azure, GCP) and their versions.|
|**Configuring the backend** | Defines where Terraform stores its state files (like local file system, S3, etc.).|
|**Enabling experimental features (optional)**| For preview or upcoming features in Terraform.|

Example: 
```
terraform {
  required_version = ">= 1.3.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }

  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "prod/terraform.tfstate"
    region         = "us-west-2"
    encrypt        = true
    dynamodb_table = "terraform-locks"
  }
}
```
### 2. Provider Block:

Terraform providers are plugins that allow Terraform to interact with different APIs and services. They define the resources and data sources available for provisioning and managing infrastructure. Each provider is specific to a service or platform, like AWS, Azure, Google Cloud, or Kubernetes.

Here's a detailed breakdown of what the provider block does and why it's essential:

#### 1. Required_providers in the terraform block:
- While the provider block configures how to connect to a provider, the required_providers block (inside the terraform block) declares which providers your configuration needs and optionally specifies their version constraints.
- This is crucial for ensuring consistency and compatibility across different Terraform runs and team members. Terraform uses this information during terraform init to download the correct provider versions.

Syntax:
```
terraform {
  required_version = ">= 1.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 4.0"
    }

    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 3.0"
    }

    google = {
      source  = "hashicorp/google"
      version = "~> 4.0"
    }

    hcp = {
      source  = "hashicorp/hcp"
      version = "~> 0.1"
    }

    # Optional: Terraform Enterprise (for running Terraform Enterprise in an automated way)
    tfe = {
      source  = "hashicorp/tfe"
      version = "~> 0.33"
    }
  }

}
```
#### 2. Provider block in terraform block:
  
   - Every provider block starts with the provider keyword, followed by the provider's name (e.g., aws, azurerm, google, kubernetes, docker, github).
   - This tells Terraform which specific plugin it needs to download and use.
   - **Configuring Authentication and Connection:**
       * Inside the provider block, you provide arguments that configure how Terraform authenticates and connects to the provider's API.

         **Example for AWS:**
           ```
           terraform {
              required_version = ">= 1.0"

              required_providers {
                   aws = {
                     source  = "hashicorp/aws"
                     version = "~> 4.0"
                   }
               } 
              provider "aws" {
                 region = "us-east-1"
                 # access_key = "YOUR_ACCESS_KEY" # Not recommended for sensitive info
                 # secret_key = "YOUR_SECRET_KEY" # Not recommended for sensitive info
                 // AWS credentials are typically sourced from environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY)
                 // or the AWS shared credentials file (~/.aws/credentials)
             }
           }
           ```
         **Example for Azure:**
           ```
           terraform {
              required_version = ">= 1.0"

             required_providers {
                azurerm = {
                  source  = "hashicorp/azurerm"
                  version = "~> 3.0"
                   }
               }

              provider "azurerm" {
                features {} # Required for recent versions of azurerm provider

                # client_id       = "..."
                # client_secret   = "..."
                # subscription_id = "..."
                # tenant_id       = "..."
                // Azure credentials are typically sourced from environment variables
                // (ARM_CLIENT_ID, ARM_CLIENT_SECRET, ARM_SUBSCRIPTION_ID, ARM_TENANT_ID)
                // or Azure CLI login (az login)
              }
           }
           ```
         **Example for GCP:**
           ```
           terraform {
              required_version = ">= 1.0"

              required_providers {
                google = {
                  source  = "hashicorp/google"
                  version = "~> 4.0"
                   }
               }

              provider "google" {
                credentials = file("<PATH_TO_YOUR_SERVICE_ACCOUNT_JSON>")
                project     = "<YOUR_PROJECT_ID>"
                region      = "us-central1"
                zone        = "us-central1-a"
              }

           }
           ```

#### 3. Enabling Resource Management:

  * Once a provider is declared and configured, Terraform gains the ability to manage resources offered by that provider.
  * For instance, if you declare the aws provider, you can then define aws_instance, aws_vpc, aws_s3_bucket resources in your configuration.

    **Example:**
    ```
    terraform {
      required_version = ">= 1.0"

      required_providers {
        aws = {
          source  = "hashicorp/aws"
          version = "~> 4.0"
         }
      }
      resource "aws_s3_bucket" "my_bucket" {
        bucket = "my-unique-bucket-name-123456"
        acl    = "private"

        tags = {
          Name        = "My bucket"
          Environment = "Dev"
        }
      }
    }  
    ```

#### 4. Multiple Provider Configurations (Aliases):

  * Sometimes, you might need to interact with the same provider in different regions or with different sets of credentials within a single Terraform configuration.
  * You can achieve this by using the alias argument in the provider block. This creates distinct configurations of the same provider type.
  * You then specify which aliased provider to use for a particular resource using the provider argument within the resource block.

**Aliases aws provider examples:**
  ```
  terraform {
    required_version = ">= 1.0"

    required_providers {
      aws = {
        source  = "hashicorp/aws"
        version = "~> 4.0"
      }
    }
    provider "aws" {
      region = "us-east-1"
      alias  = "virginia"
    }

    provider "aws" {
      region = "us-west-2"
      alias  = "oregon"
    }

    resource "aws_instance" "web_virginia" {
      provider      = aws.virginia # Use the aliased provider
      ami           = "ami-0abcdef1234567890"
      instance_type = "t2.micro"
      tags = {
        Name = "Web_VA"
      }
    }

    resource "aws_instance" "web_oregon" {
      provider      = aws.oregon # Use the aliased provider
      ami           = "ami-0fedcba9876543210"
      instance_type = "t2.micro"
      tags = {
        Name = "Web_OR"
      }
    }
  }
  ```
### 3. Backend Block:

In Terraform, a backend defines where and how Terraform stores its state. By default, Terraform stores state locally (terraform.tfstate), but using a backend allows remote state management, locking, and collaboration—especially important in team environments.

Common Terraform Backend Types and Examples:
Terraform supports a wide variety of backend types, including:

1. **local (default):**
   ```
   terraform {
     backend "local" {
       path = "terraform.tfstate"
     }
   }
   ```
   
2. **s3 (Amazon S3):** A very popular choice, often combined with DynamoDB for state locking.
   ```
   terraform {
     backend "s3" {
       bucket         = "my-terraform-state-bucket"
       key            = "path/to/my/terraform.tfstate"
       region         = "us-east-1"
       dynamodb_table = "my-terraform-state-lock" # For state locking
       encrypt        = true                     # Enable server-side encryption
     }
   }
   ```
   
3. **azurerm (Azure Blob Storage):**
   ```
   terraform {
     backend "azurerm" {
       resource_group_name  = "my-terraform-rg"
       storage_account_name = "myterraformstate"
       container_name       = "tfstate"
       key                  = "path/to/terraform.tfstate"
     }
   }
   ```
   
4. **gcs (Google Cloud Storage):**
   ```
   terraform {
     backend "gcs" {
       bucket = "my-gcs-terraform-state"
       prefix = "terraform/state" # Path within the bucket
     }
   }
   ```
   
5. **remote (Terraform Cloud/Enterprise):**
   ```
   terraform {
     cloud {
       organization = "my-organization"
       workspaces {
         name = "my-workspace"
       }
     }
   }
   ```
   
### 4. Resource Block:

A Terraform resource block is the core component of a Terraform configuration. It's how you tell Terraform what infrastructure objects you want to create, manage, and update.

##### Each resource block describes one or more infrastructure objects, such as:

* **AWS:** An EC2 instance, an S3 bucket, a VPC, an RDS database, a security group.
* **Azure:** A Virtual Machine, a Resource Group, a Storage Account, a Virtual Network.
* **Google Cloud:** A Compute Engine instance, a Cloud Storage bucket, a VPC network.
* **Kubernetes:** A Deployment, a Service, a Pod.
* **Other APIs:** A user in GitHub, a DNS record in Cloudflare, an entry in a custom API.


#### Structure of a resource Block:

![image](https://github.com/user-attachments/assets/756230ae-eab9-4d5c-a79c-35e9fd854510)

**Syntax:**
```
resource "<PROVIDER_NAME>_<TYPE>" "<LOCAL_NAME>" {
  # Argument 1 = Value 1
  # Argument 2 = Value 2
  # ...
  # Nested blocks, if any
}
```
Let's break down each part:

1. **resource keyword:** This keyword signifies that you are defining an infrastructure resource.

2. **<PROVIDER_NAME>_<TYPE> (Resource Type)**:
   * This is a string that uniquely identifies the type of resource being managed.
   * It's composed of two parts, separated by an underscore:
     - **PROVIDER_NAME:** The name of the Terraform provider responsible for managing this resource (e.g., aws, azurerm, google, kubernetes).
     - **TYPE:** The specific type of resource within that provider (e.g., instance, s3_bucket, virtual_machine, vpc).
 **Examples:** aws_instance, azurerm_resource_group, google_compute_instance.

3. **<LOCAL_NAME> (Local Name):**
   * This is a name you define to uniquely identify this particular instance of the resource within your Terraform configuration.
   * It's an identifier used only within your Terraform code. It doesn't necessarily correspond to the actual name of the resource in the cloud provider (though you often use a resource attribute to set the cloud-provider name).
   * It must be unique within its module.
   * **Purpose**: It allows you to reference this resource from other parts of your configuration (e.g., to get its ID, IP address, or other attributes).
   * **Examples:** my_web_server, main_bucket, dev_rg.

### 5. Variables Block:

In Terraform, the variable block is used to define input variables that allow your configuration to be dynamic, reusable, and customizable across different environments (e.g., dev, staging, prod).

**Syntax:**

```
variable "<NAME>" {
  type        = <TYPE>       # optional (ex: e.g., string, number, bool, list, map, object)
  default     = <VALUE>      # optional
  description = "<TEXT>"     # optional
  sensitive   = true|false   # optional
}
```
**Common Variable types:**
- **string**: For text values (e.g., "us-east-1", "production").
- **number**: For numeric values (e.g., 80, 443).
- **bool**: For boolean values (true or false).
- **list(<TYPE>)**: For ordered collections of values of a specific type (e.g., list(string)).
- **map(<TYPE>)**: For key-value pairs where all values are of a specific type (e.g., map(string)).
- **object({<KEY> = <TYPE>, ...})**: For more complex, structured data with specific keys and types.
- **any**: Allows any type, but generally less recommended as it reduces type safety.

**Examples:**

**1. Simple String Variable:**
```
variable "region" {
  type        = string
  default     = "us-west-2"
  description = "The AWS region to deploy resources in"
}
```
**2. Number Variable:**
```
variable "instance_count" {
  type        = number
  default     = 2
}
```
**3. Boolean Variable:**
```
variable "enable_logging" {
  type    = bool
  default = true
}
```
**4. List of Strings:**
```
variable "availability_zones" {
  type    = list(string)
  default = ["us-west-2a", "us-west-2b"]
}
```
**5. Map of Strings:**
```
variable "tags" {
  type = map(string)
  default = {
    Environment = "dev"
    Owner       = "team-a"
  }
}
```
**6. Sensitive Variables:**
```
variable "db_password" {
  type      = string
  sensitive = true
}
```
**Note:** When sensitive = true, Terraform hides the value in logs and plans.

**7. Object variable:**
```
variable "instance_config" {
  type = object({
    name           = string
    instance_type  = string
    ami_id         = string
    tags           = map(string)
  })

  description = "Configuration for the EC2 instance"
}
```
8. **Nested Object example:**
```
variable "app_config" {
  type = object({
    db = object({
      host = string
      port = number
    })
    enabled = bool
  })
}
```

#### How to use variables in your configuration:
You access the value of an input variable using the var. prefix followed by the variable's name:
```
${var.<VARIABLE_NAME>}
```
**Example:**
 
**variables.tf** file:
```
# variables.tf
variable "region" {
  description = "AWS region to deploy resources into."
  type        = string
  default     = "us-east-1"
}

variable "instance_type" {
  description = "The EC2 instance type."
  type        = string
  default     = "t2.micro"
  validation {
    condition     = contains(["t2.micro", "t3.small", "t3.medium"], var.instance_type)
    error_message = "Invalid instance type. Must be t2.micro, t3.small, or t3.medium."
  }
}

variable "ami_id" {
  description = "The ID of the AMI to use for the EC2 instance."
  type        = string
  sensitive   = true # Mark as sensitive if it might contain private AMI details
}
```
**main.tf** file
```
# main.tf
resource "aws_instance" "web_server" {
  ami           = var.ami_id
  instance_type = var.instance_type
  region        = var.region # Using the 'region' variable
  tags = {
    Name = "WebServer-${var.region}" # Using 'region' in a tag
  }
}
```

#### How to assign values to variables:

Terraform allows you to provide variable values in several ways, with a specific order of precedence (later methods override earlier ones):

**1. Command-line flags (-var)**:
```
terraform apply -var="region=eu-west-1" -var="instance_type=t3.small"
```

**2. Command-line flags (-var-file):**
You can specify one or more variable definition files (conventionally .tfvars or .tfvars.json).
```
# variables.tfvars
region        = "ap-south-1"
instance_type = "t3.medium"
ami_id        = "ami-0abcdef1234567890"

terraform apply -var-file="variables.tfvars"
```
**3. terraform.tfvars file (automatically loaded):**

Terraform automatically loads a file named terraform.tfvars (and terraform.tfvars.json) in the current working directory if it exists. This is a very common way to set default values for a specific environment.

**4. .auto.tfvars files (automatically loaded):**

Terraform automatically loads any file ending with .auto.tfvars (or .auto.tfvars.json) in the current working directory. This is useful for environment-specific variables, often managed by CI/CD pipelines.

**5. Environment variables (TF_VAR_ prefix):**

Terraform looks for environment variables with the prefix TF_VAR_ followed by the variable name.
```
export TF_VAR_region="ap-southeast-2"
export TF_VAR_ami_id="ami-abcdef1234567890" # For sensitive variables, use this with caution in shared environments
terraform apply
```

**6. Interactive prompt (if no default and no value provided):**

If a required variable has no default and no value is provided through the above methods, Terraform will prompt the user to enter a value during terraform plan or terraform apply.

#### Terraform Variable order of precedency(from Lowest to Highest):

1. default value in variable block
2. Environment variables (TF_VAR_...)
3. terraform.tfvars
4. terraform.tfvars.json
5. *.auto.tfvars and *.auto.tfvars.json (lexical order means alphabetical order)
6. Command-line -var and -var-file (order of appearance)

**example:**
```
terraform apply -var="region=us-east-2" -var-file="prod.tfvars"
# The value from prod.tfvars would override if 'region' was also set via -var
# Conversely:
terraform apply -var-file="prod.tfvars" -var="region=us-east-2"
# The -var flag here would override the value from prod.tfvars

```
### 6. Output Block

The output block in Terraform is used to define output values for your Terraform configuration or module. Think of outputs as the "return values" of your Terraform configuration. They are crucial for several reasons:

* **. Displaying important information to the user:** After an apply, you might want to show the public IP address of a server, a DNS name, a connection string for a database, or the ID of a newly created resource.
* **Passing data between Terraform configurations/modules:** This is a cornerstone of building modular and interconnected infrastructure. One Terraform configuration (e.g., a VPC module) can output values (like VPC ID, subnet IDs, security group IDs) that another configuration (e.g., an application deployment) can then consume using a data "terraform_remote_state" block.
* **Integration with CI/CD pipelines:** CI/CD systems often need specific outputs from Terraform (e.g., the URL of a deployed application) to proceed with subsequent steps (like running tests or updating DNS records).
* **Debugging and Inspection:** Outputs provide a quick way to inspect the values of certain attributes during development and debugging.

Syntax of an output block:
```
output "<name>" {
  value       = <expression>
  description = "What this output means"  # optional
  sensitive   = true | false              # optional
}
```
**How to use output blocks:**

1. Displaying outputs after terraform apply:
2. Querying outputs with terraform output:
3. Accessing outputs from a child module:
4. Consuming outputs from a remote state:

**Examples:**

```
#### Output AWS Instance Public IP ####
output "instance_public_ip" {
  value       = aws_instance.my_instance.public_ip
  description = "The public IP of the EC2 instance"
}
###### Output a Variable #######

  value = var.region

###### Marking an Output as Sensitive #####
```

### 8. Dynamic Block:

In Terraform, a dynamic block is used to generate nested blocks dynamically—especially useful when the number of nested blocks is not fixed or is based on input variables.

This is most commonly used in resource blocks that accept repeated nested blocks like ingress, egress, tags, rules, etc

**Syntax:**
```
dynamic "<block_label>" {
  for_each = <collection>
  content {
    # Nested arguments of the block
  }
}
```
Example: Dynamic ingress Rules for a Security Group

```
variable "ingress_rules" {
  type = list(object({
    from_port   = number
    to_port     = number
    protocol    = string
    cidr_blocks = list(string)
  }))
  default = [
    {
      from_port   = 80
      to_port     = 80
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    },
    {
      from_port   = 22
      to_port     = 22
      protocol    = "tcp"
      cidr_blocks = ["10.0.0.0/8"]
    }
  ]
}

##### Use dynamic block: ######
resource "aws_security_group" "example" {
  name = "example-sg"

  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.from_port
      to_port     = ingress.value.to_port
      protocol    = ingress.value.protocol
      cidr_blocks = ingress.value.cidr_blocks
    }
  }

  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}
```

### 9. Data Block:
In Terraform, a data block is used to fetch and reference existing resources or information that Terraform didn’t create itself. This is especially useful when you want to look up details (like AMIs, VPC IDs, secrets, etc.) and use them in your configurations.

```
data "<PROVIDER>_<DATA_SOURCE>" "<NAME>" {
  # configuration arguments
}
```
* **<PROVIDER>_<DATA_SOURCE>** This specifies the type of data you want to retrieve and the provider responsible for it (e.g., aws_ami, azurerm_resource_group, google_compute_image).
* **<NAME>:** This is a local name you give to this specific data source block. You'll use this name to reference the retrieved data elsewhere in your configuration. This name must be unique within the module.

#### How to use data from a data block:

Once a data block is defined, you can access its attributes using interpolation syntax:
```
${data.<PROVIDER>_<TYPE>.<NAME>.<ATTRIBUTE>}
```

**Examples:**

##### 1. AWS AMI Lookup
```
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["amzn2-ami-hvm-*-x86_64-gp2"]
  }
}

####Usage:####

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t2.micro"
}
```

##### 2. GCP Project Information

```
data "google_project" "current" {}

#####Usage###:

output "project_number" {
  value = data.google_project.current.number
}
```



### 10. Moved Block:

In Terraform, the moved block is used in the terraform block to tell Terraform how a resource address has changed—for example, if you renamed or refactored a resource. This helps Terraform avoid destroying and recreating the resource, and instead moves the state from the old address to the new one.

**Syntax:**
```
terraform {
  moved {
    from = <old_address>
    to   = <new_address>
  }
}

```
##### Common Use Cases for the moved Block:

**1. Renaming a Resource:**
```
############ Old-Resource ##################
resource "aws_instance" "app_server" {
  # ...
}
```

```
############ New-Resource ####################
resource "aws_instance" "web_server" { # Renamed
  # ...
}

moved {
  from = aws_instance.app_server
  to   = aws_instance.web_server
}
```
**Note:** Now Terraform will treat this as a rename, not a replacement.

**Other Use Cases:**

2. Moving a Resource into a Module
3. Moving a Resource out of a Module
4. Renaming a Module Call
5. Adding count or for_each to an existing resource
